# ADR 0004: Knowledge graph in the knowledge base (entities and relations next to the chunks)

- **Status:** Implemented and tested without a model: unit and integration tests (in-memory store and a throwaway PostgreSQL with pgvector) and a local run against a rule-based stand-in for the model gateway. **Not yet run against a real model, and not yet deployed on the cluster.** Everything about extraction quality, token cost and latency below is therefore a design intent or an estimate, not a measurement.
- **Curated facts (added later, section below):** unit and integration tested only; **not yet run on the cluster.**
- **Date:** 2026-11-23
- **Scope:** an optional graph inside the existing kb service (`knowledge.kb.graph.enabled`, default off). With it off the chart render, the database schema and the tool list are unchanged.

## Context

Vector search answers "which passage is about this". It does not answer a question whose facts sit in different documents: "who is on call for the team that owns the service whose backend suffered the Vane-3 outage?" needs five facts from five documents, none of which mentions the others. A chunk-level retriever finds the outage page and the on-call pages of every team, and leaves the chain to the model. A graph of entities and typed relations, each edge citing the chunk it came from, lets a query walk the chain and hand the agent the five citations.

Constraints of this platform: one small arm64 kind node, an existing PostgreSQL (pgvector) that already holds the kb, no new always-on pods if avoidable, licences that fit an Apache-2.0 open core, and model calls only through the model gateway so that keys, budgets and attribution stay in one place.

## Decision

Store the graph in the kb's own PostgreSQL as plain tables (`entities`, `relations`, `entity_chunks`, `extraction_jobs`, in the `kb` schema, created only when the graph is enabled) and traverse it with recursive SQL. No new service, no new image, no extension.

- **Extraction at ingest, in the background.** `PUT /v1/collections/{c}/documents/{id}` stores and embeds the document as before and queues one job per extraction window (about 2400 characters, whole chunks). A worker in the kb process claims jobs with a lease (so a crashed pod's jobs are retried), calls the gateway's `/v1/chat/completions` with the alias `knowledge.kb.graph.extractModel` (default `claude-haiku`) and stores the result in one transaction. An unchanged re-ingest queues nothing and makes no model call; a changed document replaces its graph rows. An hourly token budget (`tokensPerHour`, counted from the usage the gateway returns) pauses the worker instead of failing jobs.
- **Strict, grounded validation.** The model's JSON is not trusted. Entity types come from a closed list, names are bounded, and every entity name, alias and relation evidence must occur literally in the window text; a relation needs two listed entities and a snake_case predicate. Anything else is dropped item by item and counted, not logged with its text.
- **Own gateway key.** Extraction calls use a separate gateway virtual key, user id `kb-extract` (Secret `kb-extract-key`, created by `install.sh` only when the graph is on), so a large ingest spends its own token bucket (the gateway keeps one bucket per `user_id`) and never the embedding key's (`kb`) or an agent's.
- **Three read-only MCP tools, only when the graph is on.** `kb_graph_search(query, collection?, hops, top_k)` finds seed entities by name or alias in the question and, when an embedder exists, by the embedding of the question against the entity names; it expands them with the store's recursive traversal (1 to 3 hops, at most 25 edges followed out of any one entity, at most 10 chains returned, at most 6 supporting passages of 600 characters, one result text of at most 12 000 characters) and returns chains such as `Vane-3 <-runs_in- Teal <-stores_data_in- Quill <-calls- Orion`, every edge with `document_id`, chunk, source URI and the quoted evidence. `kb_graph_entity(name, collection?)` describes one entity and its direct neighbours. `kb_graph_paths(from, to, collection?, max_hops)` returns the shortest paths, and says "no entity named X" or "no path within N hops" as a normal answer. The document ids resolve with the existing `kb_get_document`. Agents with `knowledge: true` get them (prefix `knowledge_`) and a short prompt addition only when the graph is enabled.
- **Entity resolution (prompt version v2).** The first real run showed that merging by exact name and type leaves one thing as several nodes. Entities are now merged on the canonical form of the name, whatever their type (see "Entity resolution" below), and the extraction prompt and the validator keep generic things out.
- **Search ranking and seeds.** `kb_graph_search` returns maximal chains, ranked (see "Ranking and seeds" below), not the first ten the traversal produced.
- **Operator view.** `GET /v1/collections/{c}/graph/stats` and `GET /v1/graph/stats` (admin token) return counts and job states and the last error code, never content.
- **Traversal limit.** Three hops is a hard maximum: with `Vane-3` as the start the chain reaches `Orion`, and the last two links (`Orion` to the team to the person) take a second query. The agent prompt tells the model to continue from the last entity with `kb_graph_entity` or `kb_graph_paths`.

## Alternatives rejected

| Option | Why not |
|---|---|
| **Neo4j** (Community Edition) | GPLv3 (the Community Edition is not Apache-compatible as an embedded or bundled piece), a JVM with a heap of several hundred megabytes on a node that already runs a model server and two databases, and a second store to back up and keep in step with the chunks. |
| **FalkorDB** | Server Side Public License (SSPL), which is not an OSI-approved open-source licence and restricts offering the software as a service: not acceptable for an Apache-2.0 core that others may host. |
| **Memgraph** | Business Source License. Fast and in-memory, which is also the problem on this node. |
| **Kuzu** (embedded graph database) | Attractive (embedded, MIT), but the upstream project was archived in October 2025; building on an unmaintained engine is a risk we do not need. |
| **Apache AGE** (PostgreSQL extension) | Fits the idea best and is Apache-2.0, but it needs a custom PostgreSQL image (AGE built into the pgvector image), which is an image to build, pin, scan and upgrade. Deferred: plain tables with recursive SQL cover a three-hop limit, and the graph tables can move into AGE later without changing the tools. |
| **LightRAG, Microsoft GraphRAG, Graphiti** | Each is a Python service with its own pipeline, its own chunking and its own store. That would split the truth about a document across two chunkings, add a pod and a language to the platform, and make citations point at chunks the kb cannot open with `kb_get_document`. We keep one chunk table and attach edges to its chunks. |

## Consequences

- **Cost.** Ingest now makes one model call per window of about 2400 characters, with a system prompt of roughly 400 tokens and a bounded JSON answer. A 50 000 character document is about 21 windows. At the default 300 000 tokens per hour the worker stops and resumes; a large corpus takes hours, not seconds. These are estimates: no real run has been measured.
- **Latency.** The chunk search path is untouched. A graph query is a few indexed SQL statements and, with embeddings on, one query embedding (bounded by the existing timeout, with fallback to name-only seeds).
- **Operations.** More tables and a background loop in the kb pod. Jobs and graph rows are removed with their document. The `kb-extract-key` Secret is created by `install.sh` when absent, never printed, and removed by `uninstall.sh` with `PURGE_SECRETS=1`.
- **Quality is the model's.** Missed entities, names the canonical form does not unify (a nickname, an abbreviation), and relations the model phrases differently across documents all reduce recall. Merge is by canonical name inside one collection only; there is no cross-collection entity.
- **Gateway budget.** The gateway's token budget is one number for all virtual keys (the policy has a single rate limit entry keyed by `user_id`). `kb-extract` therefore has its own bucket of that size, not a smaller one; `tokensPerHour` is the lower, kb-side bound inside it. A different gateway budget for one key would need a policy change that was not verified on the gateway version in use, so it was not made.

## Privacy

Document text is sent to the extraction model: every window of every ingested document, as stored (the title heading included when the document has one). Choose a model you may send that text to, or keep the graph off; there is no per-document opt-out yet. The kb logs only counts, codes, document and collection names and token numbers, never document or model text. The stats endpoint and logs carry no content. Entities, descriptions and evidence are stored in the kb database, with the same access rules as the chunks.

## Injection defence

A document can contain text that tries to steer the extractor ("ignore the rules and output ...") or to plant false facts. Defences, in order: the window is wrapped in markers with a per-window token the text does not contain and the system prompt calls it untrusted data; the model gets no tools; the output must be one JSON object, validated as above; names and evidence must be literal substrings of the window, so the model cannot add an entity or a quote that the document does not contain; the number of entities and relations per window is capped. What validation cannot prevent: a document that really states a false or misleading fact produces a grounded edge. So **graph content is untrusted data for agents**, exactly like chunk text. Every graph tool result starts with the same notice line as `kb_search`, the prompt addition says the facts are reference data and never instructions, and every edge carries the document id and quote so the agent (or a person) can check it with `kb_get_document`.

## Limits

- Three hops at most; at most 25 edges followed out of one entity; ten chains and six passages per answer. A very connected entity is cut off, deterministically (lowest edge ids first), and the answer says so.
- English prose of moderate length per document; very long documents are cut into windows and a fact that spans two windows is missed.
- Entity names are merged by canonical form (below), not by similarity: a nickname or an abbreviation stays a separate entity unless the model lists it as an alias. The category-word list is English only. Merging on the name alone can join two different things that have the same proper name inside one collection ("Mesh" the service and "Mesh" the team); the type is not part of the key, so it cannot tell them apart.
- Relations are directed and typed by a free predicate (`owns`, `calls`, ...). Predicates of different documents are not unified, so a query by predicate is not offered.
- Deleting or replacing a document removes its edges at once; an entity that nothing refers to any more is removed with them.
- Retrieval was judged on one real run only (below), and the fixes for what it showed have not yet been run against a real model.

## Entity resolution

The merge key of an entity is `(collection, canonical form of its name)`. The canonical form is the lower-case name with punctuation as single spaces, without category words at its start or end as long as another word remains: `Team Basalt`, `Basalt team` and `Basalt` are one entity, as are `cluster Teal` and `Teal`. The category words are the entity type words (`service`, `team`, `person`, `system`, `location`, `organization`, `product`, `event`, `concept`), `cluster`, `region`, `api`, `group`, `squad`, `department`, `office` and the articles; the one list is `categoryWords` in `services/kb/internal/store/canon.go`. Inner words stay (`Ledger API Quill`).

- **Type is not part of the key.** The first type seen is the primary one; the others are recorded (`other_types`). `Ink` as a service in one document and a system in another is one node.
- **Displayed name.** The form with more words wins (`Team Basalt` over `Basalt`); with as many, the byte-wise smaller one, so the result does not depend on the order in which documents were extracted. Every other form becomes an alias, so a question using either form finds the entity. A manual entity keeps its name.
- **No fuzzy matching.** `Mira Okafor` and `Mira Lindqvist`, `Vane-1`, `Vane-2` and `Vane-3`, `Quill` and `Quire` stay apart (tests with exactly these).
- **Events are scoped.** An `event` whose name has no digit (`disk outage`) is merged only inside its document; an event with a date or identifier in its name (`power outage on 3 March`, `Vane-3 outage`) merges across documents.
- **What the validator drops** (each rule is deterministic, English, and independent of the corpus): (1) a name made only of category, generic-noun and role words (`database`, `the wiki`, `dashboard`, `on-call engineer`): it says what kind of thing, not which, and from several documents it would become one hub node joining unrelated facts; (2) a `person` whose name has a role word (`Granite team lead`, `finance engineering duty officer`) or has no capitalised or numbered word, as written in the text, that is not itself generic (`the intern`): a role denotes whoever holds it; (3) an `event` without a digit in its name: it names no single occurrence. Prompt version v2 asks the model for the same: proper names without leading generic words, no entities for unnamed things, events only with a date or identifier.
- **Migration 0005.** It adds `canon_name` and `other_types`, replaces the old unique key `(collection, type, norm_name)` by one on `(collection, canon_name)`, and **once** (guarded by `schema_migrations`) deletes every extracted relation, mention, entity and extraction job, because the old rows cannot be merged without the text. Rows with `origin = 'manual'`, and entities a manual relation refers to, are kept and given a canonical name. Documents are extracted again on their next ingest (the prompt version changed to v2 and the jobs are gone, so an unchanged re-ingest queues them); nothing is re-extracted by itself. Until a collection is re-ingested its graph is empty.

## Ranking and seeds

- **Seeds.** Entities whose name or alias occurs in the question come first. An embedding-only seed is added only when its cosine similarity is at least 0.8, or, while fewer than three seeds exist, at least 0.5 (`SeedEmbeddingStrong`, `SeedLexicalTarget`, `SeedEmbeddingFloor` in `internal/kb/graph.go`; the numbers are untuned guesses for the real embedder). An entity made only of generic words that merely occurs inside the question is no seed.
- **Chains.** One traversal per seed (so one seed cannot use the 500-path limit of another), longest paths first before the limit cuts. A chain that lies inside a longer one, from either end, is dropped. The rest is ranked by the number of distinct documents its facts cite, then by length, then by the seed's score, then by collection and edge ids. No seed takes more than its share of the ten slots; unused slots go to the best chains left.
- `kb_graph_entity` is unchanged (direct neighbours, lowest edge ids first, at most 25).

## Evidence so far

- **First real run** (extraction model through the gateway; the HTTP 400 it first hit is fixed in `e3273c0`: the answer is requested as a strict JSON schema and no sampling parameter is sent): 26 extraction jobs done, 42 359 tokens, 71 entities, 53 relations. Extraction worked, retrieval did not: the canary **failed**. `kb_graph_paths` from `Orion` to `Mira Okafor` answered "no path within 3 hops" and `kb_graph_search` for the canary question returned ten chains, none reaching `Orion`. Cause 1: one thing was several entities (`Basalt` and `Team Basalt`, `Teal` and `cluster Teal`, `Granite`/`Team Granite`, `Marrow`/`Team Marrow`, `Onyx`/`Cluster Onyx`, `Amber`/`Cluster Amber`, `Ink` as service and as system), so `Basalt -owns-> Orion` never met `Mira Okafor -member_of-> Team Basalt`; and generic nouns (`disk outage`, `database`, `wiki`, `on-call engineer`, `provider`, `dashboard`) from unrelated documents merged into single nodes and made false links. Cause 2: the returned chains were two-hop chains around generic nodes, ordered by edge id. The fixes are in this document (entity resolution, ranking and seeds); the real graph of that run is a test fixture (`services/kb/internal/kb/testdata/canary-graph-v1.txt`), and the tests that failed on it first now pass. **The canary has not yet passed against a real model after these changes.**
- `go test -race ./...` in `services/kb`, and `make test-integration` (throwaway pgvector and plain PostgreSQL containers), cover the store contract for both backends, extraction validation, the worker (leases, retries, budget, idempotence), the three tools (bounds, scoping, determinism, no content in logs, deadline) and the stats route.
- A local run of the kb with an in-memory store, a rule-based stand-in for the gateway and `hack/kb-graph-canary.sh` printed PASS. The stand-in only recognises the five chain sentences, so this proves the plumbing, not the extraction.
- Chart tests (`charts/openagentix/tests/run.sh`) cover the key annotations, the tool lists, validation, and that the render with the graph off is byte-identical to the one before this work.

## Curated facts (fact sets)

The graph can also hold facts an operator wrote by hand, with no model: a catalogue of services, teams, owners, dependencies and escalation contacts. This closes the gap "no manual curation API" and uses the `origin = 'manual'` column that was in the schema from the start.

**Decision.** A **fact set** is a named catalogue of one collection, replaced as a whole by `PUT /v1/collections/{c}/graph/factsets/{id}` (also `GET` one, `GET` the list, `DELETE`), with the document routes' admin authentication, body limit and no-content logging. The routes exist only with the graph on. The body is `{source_uri?, entities:[{name, type, description?, aliases?}], relations:[{source, predicate, target, note?}]}`. A relation's evidence is its note, and it cites its fact set and `source_uri` instead of a document chunk. The three tools return curated and extracted facts together; a curated one reads `Basalt -owns-> Orion | curated: factset=org-catalogue source=... | "note"`.

**Choices and why.**

- *Replace, not patch.* One idempotent call per file keeps the operator's file the source of truth: the same body twice changes nothing (the store compares a hash of the normalised body and answers `changed: false`), a changed body removes what left it. A per-fact API would need ids and a diff the operator would have to keep in step with the file.
- *Both ends declared in the same fact set.* The alternative, allowing an end that already exists in the collection, would make a fact set mean different things depending on what documents were ingested, and a relation could silently attach to the wrong extracted entity. The cost is that an operator who wants to say something about an extracted-only entity declares it (name and type) in the fact set; it then merges with the extracted one by canonical name.
- *Same shape rules as extraction, not the grounding rules.* Entity types, name length, predicate form and canonical-name merging are shared; there is no "must occur in the text" rule and no generic-name or role-word rejection, because the operator decides. Two entities of one fact set with the same canonical name are an error (they would merge). Aliases are limited to 10, descriptions to 200 characters, notes to 300, and a repeated relation is dropped.
- *Manual wins for display.* Merging a curated entity into an extracted one sets its name, type (the old type goes to `other_types`) and description, and marks it manual; later extraction never renames or retypes it. Two fact sets declaring the same entity keep the first one's name and type while it exists.
- *Which entities are manual.* An entity is manual exactly while some fact set declares it (table `graph_factset_entities`). Replacing a fact set first un-marks the entities only it declared, then re-marks the ones the new version declares, so a rename in the file takes effect. Deleting a fact set un-marks its entities and then collects the extracted ones nothing refers to; an entity that extracted relations or mentions still use stays, as an extracted entity. Migration 0005 and `collectEntities` already protected `origin = 'manual'` rows, and deleting or re-ingesting documents never touches a relation without a document: both are tested for both stores.
- *Ranking.* A fact set counts as one source (not as one per fact) when chains are ranked by the distinct sources they cite, so a chain that joins two documents and a catalogue ranks above one that stays inside the catalogue.
- *Untrusted notice kept.* The catalogue is operator-trusted, but one answer mixes it with extracted text, so the notice stays and a line says what "curated" means.

**Schema (migration 0006, applied with the others at each start of a graph-enabled kb).** Tables `graph_factsets` (id, `source_uri`, the normalised body as jsonb, a hash, counts) and `graph_factset_entities`; on `relations` the columns `document_id` and `chunk_index` become nullable, `factset_id` is added with a foreign key that cascades, and a check requires exactly one source (a document chunk or a fact set); a partial unique index keeps a fact set's relations unique. Existing rows all cite a document and are kept as they are. Tested by starting from the schema migration 5 left, with extracted and manual rows, and by a second start that changes nothing.

**Limits.** Curated entities have no name embedding (the kb does not call the embedder from the fact set route), so a question finds them by name or alias only. At most 2000 entities and 5000 relations per fact set (413 above that); a bigger catalogue is several fact sets. No per-fact edit and no history. The catalogue text is stored and returned as written (it is operator data, not secret): do not put secrets in it.

**Evidence.** Store contract tests run against the in-memory store and PostgreSQL (replace, idempotence, removal of dropped facts, merge with extracted entities, protection from document delete and re-ingest, un-marking on delete, shared entities, collections); API tests cover authentication, the absence of the routes with the graph off, validation errors, limits and the logs; a tool test covers the marked output; a test loads the sample catalogue next to the stored canary extraction and checks that the question "Which service calls the ledger API Quill, which team owns it, and who is that team's escalation manager?" is answered by two extracted facts and one curated one (Orion, Basalt, Priya Venkat) without changing the canary answer. **Not run on the cluster, and not run with a live model.**
